# 压测报告（完整版）

> 目标：拿到「优化前 vs 优化后」的真实数据，并说清楚瓶颈在哪里。
> 所有数据均为本机实测，不是估算值。

## 1. 测试环境

| 项 | 值 |
| --- | --- |
| 机器 | AMD Ryzen 7 8845H（8 核 16 线程），15.3 GB 内存，Windows |
| 应用 | Spring Boot 3.2.5，内嵌 Tomcat，单实例 |
| JVM | JDK 25，`-Xms512m -Xmx512m -XX:+UseG1GC` |
| 存储 | MySQL 8.4.9、Redis 5.0.14（纯内存模式）、RabbitMQ 3.13 |
| 应用日志 | `logging.level.root=warn`，MyBatis `NoLoggingImpl`（压测必须关 SQL 日志） |
| 压测工具 | JMeter 5.6.3，非 GUI（`jmeter -n -t xxx.jmx`） |
| 网络 | JMeter 与被测应用在同一台机器（客户端与服务端争抢 CPU，绝对值为下限） |

## 2. 测试计划

| 计划 | 参数 | 说明 |
| --- | --- | --- |
| `redirect-hit.jmx` | 200 线程 × 100 循环，`-Jramp=5` | 缓存命中；每线程独立 `X-Forwarded-For` 绕过 IP 限流 |
| `redirect-hit.jmx`（ramp 版） | 200 × 100，`-Jramp=60` | 验证 60 秒 ramp-up 下无连接拒绝；吞吐受线程启动速率限制，仅作参考 |
| `redirect-miss.jmx` | 200 × 1 | 冷路径：先删除 `short-link:goto:*`，200 个并发首次请求 |
| `create-concurrent.jmx` | 100 × 1，`-Jtoken=...` | 同一长链并发创建，验证数据库幂等 |
| `create-rate-limit.jmx` | 1 × 40，`-Jtoken=...` | 单用户高频创建，断言业务码为 0；被限流的 10 次记为失败（预期） |

四个计划都包含 `Summary Report`、`Aggregate Report`、`Response Time Graph` 监听器；运行时另外用 `-e -o` 生成 HTML 报告。

## 3. 压测结果

| # | 场景 | 样本 | QPS | 平均 RT | P95 | P99 | Max | 错误率 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| R1 | 缓存关闭 + Hikari=10 + **ramp 60** | 20000 | 332.9/s | 4.1 ms | 5 ms | 7 ms | 1011 ms | 0.00% |
| R1b | 缓存关闭 + Hikari=10 + **ramp 5**（基准） | 20000 | 1135.6/s | 125.1 ms | 409 ms | 703 ms | 959 ms | 0.00% |
| R2 | 缓存开启 + Hikari=20（**优化后**） | 20000 | **1385.3/s** | **88.8 ms** | 236 ms | 337 ms | 596 ms | 0.00% |
| R3 | 缓存关闭 + Hikari=20 | 20000 | 977.8/s | 158.6 ms | 514 ms | 774 ms | 1021 ms | 0.00% |
| R4 | 缓存开启 + Tomcat=400 | 20000 | 1389.3/s | 87.9 ms | 221 ms | 309 ms | 438 ms | 0.00% |
| R5 | 缓存未命中（冷路径，200 并发） | 200 | 506.3/s | 165.6 ms | 241 ms | 242 ms | 243 ms | 0.00% |
| R6 | 并发创建同一长链（100 并发） | 100 | 370.4/s | 116.3 ms | 152 ms | 155 ms | 156 ms | 0.00%（HTTP） |
| R7 | 单用户高频创建（40 次） | 40 | 64.0/s | 12.8 ms | 15 ms | 80 ms | 80 ms | 25.00%（**预期**：10 次限流） |

> R1 的 60 秒 ramp 版本：每个线程 100 次请求在 1 秒内就跑完，吞吐实际被「每秒启动约 3.3 个线程 × 100 次」限制，只适合验证 ramp-up 下无连接拒绝，不适合比较服务端容量。因此容量对比使用 R1b / R2（ramp 5）。
>
> R6 的 100 个请求受 USER 限流（30 次/60s）影响，只有约 30 个进入业务逻辑；数据库最终 `bench-d5` 记录数 = **1**，幂等成立。
>
> R7 的 10 次失败是限流器主动拒绝（业务码 `A0001`），属于该场景的预期结果，不是缺陷。

## 4. 优化前后对比

### 4.1 缓存开关（核心对比）

| 指标 | 无缓存（R1b） | 有缓存（R2） | 变化 |
| --- | --- | --- | --- |
| QPS | 1135.6/s | **1385.3/s** | **+22.0%** |
| 平均 RT | 125.1 ms | **88.8 ms** | **-29.0%** |
| P99 | 703 ms | **337 ms** | **-52.1%** |

结论：在当前已接入「实时统计 + MQ 明细」的热路径下，缓存仍带来约 **22% 的 QPS 提升** 和 **约一半的 P99 改善**。提升幅度比第 2 周小（当时是 709 → 2681，约 3.8 倍），原因是缓存命中路径仍然要执行布隆过滤、统计 Pipeline（12 条命令）和 MQ 发送，缓存省掉的 DB 查询不再是唯一大头。

### 4.2 Hikari 连接池 10 → 20

R1b（10）1135.6/s vs R3（20）977.8/s：**没有提升，差异在测量噪声范围内**。说明缓存关闭时瓶颈也不在连接池大小，而在 Redis 统计 / MQ 与单机资源竞争。

### 4.3 Tomcat 线程 200 → 400

R2（200）1385.3/s vs R4（400）1389.3/s：**基本无变化（+0.3%）**。200 线程已足够，瓶颈不在 Tomcat 线程数。

### 4.4 日志 / JVM

- 所有正式压测均使用 `root=warn` + MyBatis `NoLoggingImpl`，避免 SQL 日志与调试日志拖慢 QPS。
- 所有压测均使用 `-Xms512m -Xmx512m -XX:+UseG1GC`。
- 这两项未做单独 A/B（SQL 日志开启时 QPS 会明显下降，属于常识性优化）。

### 4.5 Redis 统计 Pipeline

第 3 周 W3D4 已把一次访问的 12 条统计命令合并成 1 次 RTT。本次压测中，缓存命中路径仍有 14+ 次 Redis 交互（布隆 + 缓存 GET + 统计 Pipeline），是当前吞吐的主要成本之一；若改回 12 次独立命令，RTT 会进一步放大。

## 5. 瓶颈分析

1. **缓存命中场景（~1.4k QPS）**：瓶颈在 **Redis 交互 + MQ 发送**。每次跳转要经过布隆过滤器、缓存 GET、统计 Pipeline、MQ publish；Hikari 与 Tomcat 调参均无提升，说明瓶颈不在数据库连接和 Web 线程。
2. **缓存未命中场景（~0.5k QPS）**：瓶颈在 **MySQL 单次查询 + 回写缓存**，200 个并发冷请求的平均 RT 为 165.6 ms。
3. **创建场景（~370/s）**：主要受 **USER 限流（30 次/60s）** 与 Redisson 锁约束；100 并发下数据库仍只有 1 条记录，幂等正确。
4. **测试机限制**：JMeter、应用、MySQL、Redis、RabbitMQ 全部在同一台 16 线程机器上，CPU 与磁盘互相争抢；绝对值应视为下限，相对对比仍然有效。

## 6. 结论与后续建议

- 当前开发机实测：**缓存命中约 1.4k QPS（P99 337ms）**，**冷路径约 0.5k QPS**，**创建约 370/s（受限流约束）**，所有正式场景错误率 **0%**。
- 想继续提升跳转 QPS，优先做「统计与明细写入的批量化/本地队列异步化」，而不是继续加线程或连接池。
- 正式对外数据建议把 JMeter 放到另一台机器，避免压测客户端与应用争抢 CPU。
- 原始数据：`jmeter/results/*.jtl` 与 HTML 报告（已在 `.gitignore` 中忽略，不入库）。

## 7. 历史数据（第 2 周 W2D7，供对比）

| 场景 | 线程 × 循环 | QPS | 平均 RT | P99 | 错误率 |
| --- | --- | --- | --- | --- | --- |
| 跳转（缓存命中，未接入 MQ/统计） | 200 × 100 | 2681.3/s | 29.6 ms | 51 ms | 0.00% |
| 跳转（缓存未命中） | 200 × 1 | 709.2/s | 104.8 ms | 151 ms | 0.00% |
| 并发创建（同一长链） | 100 × 1 | 518.1/s | 73.0 ms | 95 ms | 0.00% |

对比可以看出：第 3 周接入实时统计 + MQ 后，跳转热路径多了 Redis 统计与 MQ 写入，命中场景 QPS 从 2681 降到约 1385 —— 这是「功能换吞吐」的典型取舍，也是本报告最重要的瓶颈结论。
