# 压测报告（第一版）

> 目标：拿到「缓存命中 vs 未命中」的对比数据，作为简历里 QPS 数字的依据。

## 测试环境

| 项 | 值 |
| --- | --- |
| 机器 | 本机 Windows（开发机，非服务器） |
| 应用 | Spring Boot 3.2.5（内嵌 Tomcat，单实例） |
| 存储 | MySQL 8.4、Redis 5.0.14（C 盘副本，**纯内存模式**）、RabbitMQ 3.13 |
| 压测工具 | JMeter 5.6.3，非 GUI 模式（`jmeter -n -t xxx.jmx -l result.jtl`） |
| 被测接口 | `GET /{gid}/{shortUri}`（跳转）、`POST /api/short-link/admin/v1/link`（创建） |

测试计划：`jmeter/redirect-hit.jmx`、`jmeter/redirect-miss.jmx`、`jmeter/create-concurrent.jmx`

## 压测结果

| 场景 | 线程数 × 循环 | 样本数 | QPS | 平均 RT | P99 | 错误率 |
| --- | --- | --- | --- | --- | --- | --- |
| 跳转（**缓存命中**） | 200 × 100 | 20000 | **2681.3/s** | **29.6 ms** | 51 ms | 0.00% |
| 跳转（缓存未命中） | 200 × 1 | 200 | **709.2/s** | **104.8 ms** | 151 ms | 0.00% |
| 并发创建（同一长链） | 100 × 1 | 100 | 518.1/s | 73.0 ms | 95 ms | 0.00% |

**结论：缓存命中相比未命中，QPS 提升约 3.8 倍，平均 RT 降到约 1/3.5。**

> JMeter 原始输出
> ```
> summary =  20000 in 00:00:07 = 2681.3/s Avg: 29 Min: 1 Max: 59 Err: 0 (0.00%)     # 命中
> summary =    200 in 00:00:00 =  709.2/s Avg: 104 Min: 45 Max: 151 Err: 0 (0.00%)  # 未命中
> summary =    100 in 00:00:00 =  518.1/s Avg: 73 Min: 54 Max: 95 Err: 0 (0.00%)    # 并发创建
> ```

## 方法与偏差说明（重要）

1. **跳转接口有 IP 限流（300 次/60s）**，直接压测会被限流干扰。因此每个线程带上不同的 `X-Forwarded-For`（`10.0.0.${__threadNum}`）模拟不同客户端，每个桶 100 次请求 < 300，未触发限流。
2. **「缓存未命中」场景用 200 线程 × 1 循环**：同一个短链只有最先的请求是真正的未命中，若按排期写的 200×100，从第 2 个请求起就都是命中，测不到冷路径。这里用 200 个并发**首次**请求来取得冷路径数据。
3. **并发创建受 USER 限流（30 次/60s）影响**：100 线程里放行 30、被限流 70（`zcard short-link:rate-limit:user:zhangsan = 30`）。放行请求最终在数据库只留下 **1 条记录**，幂等成立。
   更严格的「全新长链并发创建」验证见第 2 周 D2 验收：40 并发 → `distinctFullShortUrl = 1`、DB 行数 = 1。
4. `create-concurrent.jmx` 依赖登录态，跑前需把 User Defined Variables 里的 `token` 换成登录接口返回的 token。
5. 本机 Redis 已改为纯内存模式（`appendonly no` + `save ""`），因为该机器磁盘 I/O 不稳，一落盘就 `MISCONF`；压测数据不受影响（缓存命中率即为真实表现）。
