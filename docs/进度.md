## 本周问题与解决（面试素材）

### 1. Redis AOF 写入失败导致 MISCONF，登录接口全挂

- **现象**：注册接口正常，登录接口统一返回 `B0001 系统异常`。
- **定位过程**：不是猜，而是三级排查 —— ① 看应用日志异常栈，发现 `MISCONF Errors writing to the AOF file: Input/output error`；② 用 `redis-cli` 直接 `SET` 复现同一错误；③ `INFO persistence` 查到 `aof_last_write_status:err`。
- **原因**：Redis 开了 AOF 持久化，写 AOF 文件失败后进入 **MISCONF 只读保护状态**：读命令照常，写命令一律拒绝。注册只写 MySQL 所以看不出问题，登录要写会话（`SETEX`）才暴露。
- **解决**：以 Windows 服务方式启动 Redis（`Start-Service redis`），而不是手工运行 `redis-server.exe`。
- **收获**：MISCONF 是 Redis 的自我保护而非故障本身；`aof_last_write_status` / `rdb_last_bgsave_status` 是排查持久化问题的第一入口。

### 2. Sa-Token 未登录异常被全局兜底吞掉

- **现象**：不带 token 访问接口，返回 `B0001 系统异常` 而不是 `A0006 未登录`。
- **原因**：`SaTokenExceptionHandler` 和 `GlobalExceptionHandler` 都能处理异常，但优先级不确定，`NotLoginException` 被兜底逻辑先接住了。
- **解决**：给 `SaTokenExceptionHandler` 加 `@Order(Ordered.HIGHEST_PRECEDENCE)`，明确异常处理器的优先级。
- **收获**：多个 `@RestControllerAdvice` 共存时，必须显式指定 `@Order`，否则异常被谁处理是"看运气"。

### 3. MyBatis-Plus 3.5.7 的 BaseMapper 方法重载导致单测编译失败

- **现象**：写 Mockito 单测时 `verify(mapper, never()).insert(any())` 编译报 "引用不明确"。
- **原因**：3.5.7 的 `insert` / `updateById` / `deleteById` 都有两个重载（单个对象 vs 集合），`any()` 无法推断类型。
- **解决**：显式指定类型，如 `any(TUser.class)`、`any(Long.class)`。
- **收获**：写 Mock 时尽量用带类型的匹配器，避免重载歧义，也更严谨。

### 4. 乐观锁拦截器类名拼写错误

- **现象**：启动报类找不到。
- **原因**：写成 `OptimisticLockingInnerInterceptor`，正确是 `OptimisticLockerInnerInterceptor`。
- **收获**：MyBatis-Plus 拦截器链（分页 / 乐观锁 / 防全表更新）注册顺序有讲究，类名要照官方文档核对。

### 5. Redis 序列化默认用 JDK 方式，存进去是乱码

- **原因**：`RedisTemplate` 默认 `JdkSerializationRedisSerializer`，key/value 都是不可读的二进制。
- **解决**：换成 `GenericJackson2JsonRedisSerializer`，Redis 里存的是可读 JSON，方便排查。

### 6. Spring Boot 3 的依赖必须用对应 starter

- MyBatis-Plus 3.5.7 必须用 `mybatis-plus-spring-boot3-starter`，用普通 starter 启动直接报错。
- Knife4j 4.5.0 必须用 `knife4j-openapi3-jakarta-spring-boot-starter`。
- **收获**：Spring Boot 3 迁移到 `jakarta.*` 命名空间后，第三方 starter 有专门的 boot3 版本，不能凭版本号想当然。

### 7. 数据库名不能用短横线

- **原因**：`short-link` 里的 `-` 在 SQL 中是运算符，建库/选库都要加反引号，容易踩坑。
- **解决**：统一用下划线 `short_link`。

### 8. 逻辑删除与数据隔离的设计约定

- 所有表用 `del_flag` + `@TableLogic`，删除是 `UPDATE del_flag = 1`，查询自动追加 `del_flag = 0`。
- 分组等资源接口全部做**归属校验**：先查记录，再比对 `username` 是否等于当前登录用户；**不区分"不存在"和"不属于你"，统一返回"分组不存在"**，避免通过错误信息探测他人资源是否存在。
- 密码用 BCrypt（每次加密结果不同，自带随机盐）；登录时"用户不存在"和"密码错误"返回同一个提示，**防止用户名枚举**。

### W2D1 | Base62 与短链生成策略

**产出**

| 文件 | 作用 |
| --- | --- |
| `util/Base62Util.java` | `encode(long)` / `decode(String)` / `random(int)`，三者共用同一字符集常量 |
| `util/HashUtil.java` | `md5(String)` 生成 `origin_url_hash`，是 `uk_gid_origin(gid, origin_url_hash)` 的组成部分 |
| `util/LinkUtil.java` | 拼接完整短链 `{domain}/{gid}/{shortUri}` |
| `test/Base62UtilTest.java` | 编解码互逆、边界进位、随机字符集、10 万次去重率 |

改动：`GroupServiceImpl.generateGid()` 从「UUID 前 6 位」换成 `Base62Util.random(6)`。

**验收**

- `mvn test -Dtest=Base62UtilTest` 通过（4 个用例）
- 打印 10 个随机后缀，均为 6 位且数字/小写/大写混合：`uhUaQH buwKLN 5Nxf7j uwRMVs v3Yi3z e7gzRH PxxupR rccdRk WQHt88 b4BhXx`
- 10 万次随机去重率 > 99.99%

**思考题：6 位 Base62 能表示多少条？什么情况下不够用？**

- **理论上限**：`62^6 = 56,800,235,584`，约 **568 亿** 条。
- **随机方案的真实约束不是 568 亿，而是「碰撞重试」**：设已用 n 条，新生成一条撞上的概率约 `n / 62^6`。
  - n = 568 万（N 的 0.01%）时，单次碰撞率 0.01%，3 次重试后仍失败的概率约 `1e-12`，可以忽略；
  - n = 5.68 亿（N 的 1%）时，单次碰撞率 1%，3 次重试失败率约 `1e-6`，仍可接受；
  - n 再往上，重试次数和 DB 查询次数明显上升，写性能开始下降。
  - 所以**工程上把可用容量按 N 的 1% 量级估算**（百亿级理论容量 → 亿级实际容量）更稳妥。
- **什么时候不够用**：单个命名空间内的短链量接近千万~亿级、且写入并发高时，冲突重试会变成瓶颈。
- **扩容方案**：① 长度 6 → 8 位（`62^8 ≈ 218 万亿`），新旧短链长度不一致但业务无感知；② 用分组 gid 作为命名空间隔离容量（本项目 `t_link` 的唯一索引就是 `(gid, short_uri)`，已经天然按分组隔离）。

### W2D4 | 短链跳转 + 缓存（本周第二个核心）

**产出**

| 文件 | 作用 |
| --- | --- |
| `controller/RedirectController.java` | `GET /{shortUri}`、`GET /{gid}/{shortUri}`、`GET /page/notfound` |
| `ShortLinkServiceImpl.restoreUrl(gid, shortUri)` | 完整跳转链路 |
| `resources/static/page/notfound.html` | 自定义 404 页面 |
| `common/config/SaTokenConfig.java` | 拦截范围由 `/**` 收窄为 `/api/**`（跳转对外无鉴权） |
| `application.yml` | 新增 `short-link.default-gid`（不带分组跳转时使用） |

**跳转链路（restoreUrl）**

1. 格式预校验：非 6 位 Base62 → 404，**连 Redis 都不查**
2. 布隆过滤器 `mightContain` → false 直接 404，**不查缓存不查库**（防缓存穿透第一层）
3. 查缓存：命中 `""` → 404（空值缓存）；命中有值 → 直接返回
4. 未命中 → 查库；不存在 / 已禁用 / 已过期 → 写空值缓存(TTL 60s) → 404
5. 正常 → 回写缓存（TTL = 1 天 + 随机 0~3600s）→ 302

**设计要点**

- 必须 **302** 而非 301：301 会被浏览器长期缓存，后续访问不再经过服务端，统计不到数据
- 空值统一写 `""`，与「未命中」区分开，避免空值被当成命中后又去查库
- 路径变量加正则约束（`{shortUri:[0-9a-zA-Z]{6}}`、`{gid:[0-9a-zA-Z]+}`）：既在路由层挡掉非法后缀，也避免 `/{gid}/{shortUri}` 把静态资源 `/page/notfound.html` 吃掉
- Sa-Token 拦截范围由 `/**` 收窄为 `/api/**`：跳转接口、404 页面、静态资源天然放行，白名单也只剩 4 个 API 路径

**验收（8 条全过）**

| # | 场景 | 结果 |
| --- | --- | --- |
| 1 | 创建短链指向 baidu | `http://localhost:8000/710a6a/wesV3I` |
| 2-3 | `GET /{shortUri}` | **302**，`Location: https://www.baidu.com/` |
| 4 | 第 2、3 次访问（`/{shortUri}` 与 `/{gid}/{shortUri}`） | 3 次访问控制台**只有 1 条 SELECT** → 缓存命中不查库 |
| 5 | `redis get short-link:goto:http://localhost:8000:710a6a:{shortUri}` | `https://www.baidu.com` |
| 6 | `redis ttl` 同 key | **87788**（随机区间 86400~90000，防雪崩生效） |
| 7 | `GET /q1q1q1`（不存在） | 404 页面，且控制台**无任何该后缀的 SQL/日志**（布隆拦下） |
| 8 | 把 `valid_date` 改成昨天后访问 | 404，并写入空值缓存 `""` + TTL **60**，重复访问仍 404 |

**发现的一处文档自相矛盾**

排期验收第 7 条写「访问不存在的短链 → 仍 404 且有 `""` 空值缓存」，但按文档自己给的流程（第 2 步布隆 false 就 404），**根本走不到写空值缓存那一步**。实测 `zzz999`：无 SQL、无缓存写入（`ttl = -2`）。
空值缓存真正应该验证的是「布隆认为存在、但库里不可用」的场景 —— 已用第 8 条（过期短链）覆盖。

**缓存 key 已加上 gid（修正了文档的设计缺陷）**

原 `gotoCache(domain, shortUri)` 的 key **不含 gid**，而短链后缀的唯一性是 `(gid, short_uri)`：两个分组出现相同后缀时缓存会互相覆盖，导致跳转到错误链接。
已改为 `gotoCache(domain, gid, shortUri)` → `short-link:goto:{domain}:{gid}:{shortUri}`。

复验：`GET /{shortUri}` → 302 → `https://www.bing.com/`；`redis get short-link:goto:http://localhost:8000:710a6a:neaiim` → `https://www.bing.com`（TTL 89928）；旧格式 key（不含 gid）`exists = 0`。

**验收（4 条全过）**

| # | 场景 | 结果 |
| --- | --- | --- |
| 1 | 顺序 40 次创建 | 成功 **30**、第 **31** 次起 `A0001 访问过于频繁，请稍后重试`；等 62s 后恢复 `code=0` |
| 2 | `redis zcard short-link:rate-limit:user:zhangsan` | **30**（TTL 60） |
| 3 | **50 并发**打创建 | 成功 **30** / 限流 **20**，ZSET 恰好 30 → Lua 原子性生效，不超发 |
| 4 | **320 并发**打跳转（按 IP） | 302 = **300** / 限流 **20** / 其他 0；`zcard ip:127.0.0.1 = 300` |

**踩坑（都很典型）**

1. `@Around("@annotation(rateLimit)")` 用「参数绑定」写法时启动/调用报
   `IllegalStateException: Required to bind 2 arguments, but only bound 1 (JoinPointMatch was NOT bound in invocation)`。
   改为 `@annotation(注解全限定名)` + 从方法签名反射取注解，稳定可用。
2. IDE 增量编译产生的脏 class 导致启动报 `NoClassDefFoundError: RateLimit`；`mvn clean` 重建即恢复（maven 还会打印 "Nothing to compile"，别被误导）。
3. 滑动窗口 vs 固定窗口：固定窗口有临界问题（边界前后各打满一次 = 2 倍阈值），滑动窗口用 ZSET 按时间戳精确裁剪，代价是每条请求一个 ZSET 成员（内存换精度）。

| `component/DelayedCacheDeleter.java` | 延迟双删的第 2 次删除（`@Async`，不用 ForkJoinPool） |
| `GroupService.listGids()` | 分页时限定「当前用户的分组」范围 |
| `ShortLinkServiceImpl` | `pageLink` / `updateLink` / `updateBatch` / `enableLink` / `deleteLink` / `countLink` |
| `ShortLinkController` | 补 6 个接口（page / update / updateBatch / enable / delete / count） |

**四个关键设计**

1. **数据隔离**：分页不传 gid 时，范围限定在 `groupService.listGids()`（当前用户的 gid 列表），避免看到别人的短链；传了 gid 先 `checkOwnership`。
2. **排序字段白名单**：用 `switch` 枚举固定字段，**完全不把用户输入拼进 SQL**；非法值直接返回 `A0002`。
3. **缓存一致性**：更新 / 禁用 / 删除都会删掉跳转缓存；改分组的还会同步维护新旧两个分组 Set。
4. **延迟双删**：删缓存 → 更新 DB → 延迟 500ms 再删一次，覆盖「读线程在删缓存后、更新 DB 前把旧值回填」的时间窗。

**重点坑：逻辑删除 + 唯一索引冲突**

`t_link` 的唯一索引 `uk_gid_origin(gid, origin_url_hash)` **不认 `del_flag`**：逻辑删除后记录还在表里，唯一索引位仍被占用，于是「删除后再创建同一个长链」会直接 `DuplicateKeyException`。

排期文档建议改写为 `hash + "_deleted_" + id`，但**实测行不通**：`origin_url_hash` 是 `CHAR(32)`，而 `sql-mode` 含 `STRICT_TRANS_TABLES`，写超长值会直接报 `Data too long for column`。

实际采用：**`MD5(原 hash + "_deleted_" + id)`**（仍是 32 位）——既腾出唯一索引位，又保证不同记录改写后互不相同。

**踩坑 / 观察**

1. **跳转压测必须给每个线程不同的 `X-Forwarded-For`**，否则会被自身的 IP 限流（300/60s）挡住，压出来的全是限流响应。
2. **「缓存未命中」场景不能用 200×100**：同一个短链只有最先的请求是冷路径，第 2 个请求起就是命中。这里用 200 线程 × 1 循环取冷路径数据。
3. 请求体是**非法 JSON** 时，`HttpMessageNotReadableException` 会落到全局兜底返回 `B0001 系统异常`；严格说应归一为 `A0002 参数校验失败`（已知小缺口，未改）。
4. PowerShell 写验收脚本的两个坑：`$o | ConvertTo-Json` 会把 hashtable 拆成键值对数组（要用 `-InputObject`）；双引号字符串里 `$obj.prop` 不会展开（要用 `$($obj.prop)`）。
